Email Ingestion & Hardened Sync System ​

1. Executive Summary ​

The Email Ingestion System provides a high-reliability bridge between financial email sources (bank alerts, statements) and the core finance engine. This document serves as both the architectural overview and technical specification for the hardened sync pipeline.

2. Architecture & Data Flow ​

3. Technical Specifications ​

3.1 IMAP Stability (UID-Based Sync) ​

Standard IMAP sequence numbers are volatile and reset upon mailbox re-indexing. The system now uses IMAP UIDs, which are persistent unique identifiers. This ensures that the system's "last synced" pointer remains accurate even if the user moves or deletes emails in their provider's UI.

3.2 HTML Cleaning & Pre-Extraction Ignore Filtering ​

Bank emails often use complex nested tables. Aggressive tag-stripping typically results in a single-line string that regex extractors cannot process.

  • Layout Preservation: The cleaner replaces <tr>, <br>, <p>, and <div> tags with \n before stripping remaining HTML.
  • Pre-Extraction Ignore Rules: Before calling the extraction microservice, EmailSyncService evaluates IngestionService.check_ignore_rules() against the tenant's SpamFilter and IgnoredPattern rules, immediately discarding matched mail while logging outcome = "ignored_by_rule" so users can later unblock via Allow.
  • Strict Non-Financial Classification: FinancialClassifier.is_financial(..., source="EMAIL") plus structured bank parsers filter out promotional offers, cashbacks, and OTP alerts.

3.3 Sender Normalization & Routing ​

Email "From" headers are normalized to a clean format (lowercase email only) to ensure reliable routing to custom bank-specific handlers:

  • Raw: HDFC Bank <alerts@hdfcbank.net>
  • Normalized: alerts@hdfcbank.net

4. Observability (Unified Ingestions & Sync Activity) ​

The system provides granular transparency into every email processed without exposing internal parser class names to end users.

4.1 Log Hierarchy ​

  • EmailSyncLog: Records the overall session (start time, status, total items).
  • EmailSyncItemLog: Records the result for each individual email (raw_content, normalized outcome, sanitized reason, and details_json).

4.2 Data Points Captured ​

  • Full Content (raw_content): Cleaned email body preserved for user inspection in Settings → Ingestions.
  • Outcome (outcome): Plain-English status (added_to_ledger, moved_to_triage, statement_queued, blocked_unlinked_account, duplicate_skipped, ignored_by_rule, ignored_non_financial, unrecognized_alert).
  • Reason (reason): Consumer-friendly explanation for what happened to the email.
  • Transaction / Account Link: Direct link to the created Transaction, PendingTransaction, or unlinked account mask.

5. Unified Parsing Pipeline ​

Email ingestion follows the Unified Parsing Pipeline priority:

  1. Registered Bank Parsers
  2. DB Regex Patterns
  3. AI Fallback

Both Transaction Alerts and Statement PDFs share this underlying extraction engine to ensure consistency across all data sources.
