Unified Parsing & Ingestion Pipeline ​

This document details the stateless, multi-tiered parsing strategy and two-tier deduplication architecture used to process raw financial data (SMS, Email, Statements, and CAS).

1. Stateless Architecture & Execution Hierarchy ​

The Financial Parser Microservice (Parser, port 8001) operates as a 100% stateless, in-memory stream processor. It persists zero transactional data, zero customer PII, and zero database tables at rest.

Parsing Hierarchy (Priority Stack) ​

PriorityLayerImplementationSpeedConfidence
1Compiled Bank RegistryNative Python parsers for 23+ Indian banks (HDFC, ICICI, SBI, Axis, Kotak, IndusInd, etc.) with 100+ compiled regexes.< 0.5 ms95%+
2Statement & CAS ExtractorsSpecialized table and transaction extractors (pdfplumber, casparser, UniversalParser).10–50 ms95%+
3Heuristic NormalizersFast-fuzz merchant alias normalization (rapidfuzz in-memory), safe decimal conversion, and date extraction.< 0.1 ms90%

NOTE

All runtime dependencies on external AI/LLMs (such as Gemini) have been retired in favor of high-performance, deterministic compiled Python parsers. This guarantees sub-millisecond parsing latencies, zero cloud API costs, and full offline resilience.

2. Two-Tier Deduplication Architecture ​

Deduplication operates across two strictly decoupled layers to ensure maximum throughput without losing any financial integrity:

Tier 1: Ingestion Network Idempotency (Parser In-Memory LRU) ​

  • Component: RecentSubmissionCache in [Parser/core/pipeline.py](file:///c:/Users/oksbw/Desktop/Workspace/Wealthfam/Parser/core/pipeline.py).
  • Mechanism: Thread-safe sliding-window cache storing SHA-256(tenant_id:source:content) with a 5-minute TTL (max 5,000 entries).
  • Purpose: Instantly deflects network retries from mobile background listeners or email sync pollers without touching disk or allocating database locks.
  • Outcome: Returns status: "duplicate_submission" in $\approx 0.05$ ms.

Tier 2: Authoritative Financial Ledger Deduplication (Backend PostgreSQL) ​

  • Component: TransactionDeduplicator in [Backend/app/modules/ingestion/deduplicator.py](file:///c:/Users/oksbw/Desktop/Workspace/Wealthfam/Backend/app/modules/ingestion/deduplicator.py).
  • Mechanism: Multi-tier cross-source matching against persistent PostgreSQL ledger (transactions & pending_transactions tables):
    1. Normalized UTR / Reference ID: Strips prefixes and leading zeros (normalize_ref_id) to match identical banking references.
    2. Canonical Content Hash: Generates MD5(tenant_id:account_id:date:amount:type:normalized_vendor). Uses date.date() so that an SMS alert and an Email alert arriving at different timestamps produce the exact same hash.
    3. Resilient 3-Day Window & Fuzzy Vendor: Checks [date - 1d, date, date + 1d], matches exact monetary amount, and verifies token-intersection fuzzy merchant matching across descriptions.
    4. Geolocation Enrichment: If an incoming duplicate SMS carries GPS coordinates (latitude, longitude) from the Android background listener, the backend retroactively updates the existing ledger transaction rather than discarding the metadata.

3. Observability & Operations Architecture ​

3.1 Consumer Ingestion Feed (Web-App & Mobile-App) ​

  • Consumer users interact exclusively with the Backend (:8000).
  • Every ingested SMS and Email records its raw_content and plain-English outcome in PostgreSQL (ingestion_events and email_sync_item_logs).
  • Users manage personal Ignore/Allow rules and review triage items via Settings → Ingestions without ever seeing internal parser names, regex code, or container endpoints.

3.2 Operator Parser Studio & Training Inbox (Admin-Web) ​

  • Dedicated administrative control plane on Port 8080 / :5174, backed by Admin-Backend (:8002) and telemetry.duckdb.
  • Native Registry Inspector: Inspects all 23+ built-in bank parsers and their live regex patterns.
  • Interactive Sandbox: Safely tests SMS, Email text, and password-protected PDF bank statements without writing to production ledgers.
  • Training Inbox: Displays user-submitted unrecognized alerts, strictly scrubbed of personal PII via FormatPreservingAnonymizer before presentation.

3.3 Batch Processing Engine (BatchIngestionPipeline) ​

  • High-throughput chunked ingestion (POST /v1/ingest/batch) designed for email sweep batches (50+ items).
  • Defensive Input Coercion: Automatically strips and coerces None values for subject, sender, and content, preventing runtime crashes when client JSON payloads carry null fields.
  • Sender Domain Verification: Dispatches sender to p.can_handle(subject, content, sender=sender) for all bank email parsers (e.g. IDBI, PNB, Canara, BoI, AU Bank) to confirm genuine sender authenticity.
  • Date Hint Forwarding: Converts received_at timestamps into date_hint objects, allowing parsers to accurately resolve incomplete bank alert dates lacking year or seconds.

4. Multi-Tenancy & Data Isolation ​

  • Stateless Parser: Zero customer data at rest. Operates globally for all tenants using stateless HTTP request/response payloads with short-lived JWT authentication.
  • Backend Ledger: Every transaction, account, category rule, and merchant alias is strictly isolated by tenant_id in PostgreSQL with row-level tenant filtering.
