Unified Parsing Pipeline ​

This document details the multi-tiered parsing strategy used to process raw financial data (SMS, Email, and Statements).

1. Parsing Hierarchy (Priority Stack) ​

To ensure high reliability and minimize reliance on expensive/unpredictable AI models, the system follows a strict execution order:

PriorityLayerDescriptionConfidence
1Registered ParsersHardcoded logic for specific banks (e.g., HdfcEmailParser).95%+
2Pattern ParsersRegex-based rules defined by the user or learned from training.90%
3AI FallbackLarge Language Models (Gemini) used as a last resort for unknown formats.85%

1.1 Goal: < 1% AI Usage ​

The system is designed to "learn" from AI successes. When an email is successfully parsed by AI, it can be used to generate a Pattern Rule, moving that specific format into the Tier 2 (Regex) layer for all future occurrences.

2. Orchestration Logic ​

The BatchIngestionPipeline (in the Parser Microservice) orchestrates this flow:

  1. Classification: Verify the content is financial.
  2. Static Sweep: Iterate through all RegisteredParsers in the ParserRegistry.
  3. Pattern Match: Run the PatternParser against the database of regex rules.
  4. AI Guardrail: Check if the content is "AI-worthy" (contains numbers, keywords).
  5. AI Batching: Group unknown items and send to Gemini.

3. Observability & Operations Tools ​

3.1 Consumer Ingestions Feed (Web-App & Mobile-App) ​

Every ingested SMS (IngestionEvent) and Email (EmailSyncItemLog) persists its message content (raw_content) and plain-English outcome. Consumer apps inspect results, manage Ignore/Allow rules, and submit consented anonymized unrecognized alerts through Settings → Ingestions (Web) or Ingestions (Mobile) via Backend, with zero exposure to internal parser names or regex rules.

3.2 Operator Parser Studio (Admin-Web) ​

The Parser Studio & Sandbox lives exclusively inside Admin-Web (Port 8080 / :5174), backed by Admin-Backend, allowing operators to inspect built-in parsers, author declarative templates, test raw alerts safely, and triage consented anonymized training samples.

4. Multi-Tenancy & Data Isolation ​

All parsing rules and logs are strictly partitioned by tenant_id.

  • Registered Parsers: Shared across all tenants (Global).
  • Pattern Rules: Tenant-specific (unless marked as Global by Admin).
  • Extraction Logs: Tenant-specific.
