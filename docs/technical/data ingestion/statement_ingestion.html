Bank Statement Ingestion Pipeline ​

This document outlines the end-to-end flow for automated and manual bank statement ingestion, parsing, and reconciliation.

System Overview ​

The ingestion pipeline is designed to securely fetch, decrypt, parse, and reconcile financial statements with minimal user intervention. It supports both automated email synchronization and manual uploads.

Mermaid Flow Diagram ​

Detailed Component Breakdown ​

1. Discovery & Fetching ​

  • Email Configuration: Users provide IMAP credentials. The system stores the last_sync_at timestamp to prevent duplicate scans.
  • Pattern Matching: Subject lines and senders are searched for financial/CAS statements (statement, e-statement, Consolidated Account Statement, camsonline). Only .pdf attachments are considered.
  • Pre-Vault Ignore Rules (source="STATEMENT"): Before attempting decryption, saving to Vault, or creating a Statement row, _process_email_message decodes MIME From, Subject, and filename headers and checks PostgreSQL spam_filters rules via IngestionService.check_ignore_rules(..., source="STATEMENT"). Matching promotional/margin/TDS PDFs increment count_blocked and are skipped cleanly without polluting Vault or Statements.

2. The Decryption Engine (StatementPasswordService) ​

The decryption system is encapsulated within a modular service (StatementPasswordService in Backend/app/modules/ingestion/password_service.py), utilizing a tiered authentication hierarchy:

  1. Manual Input (Absolute Priority): Explicit user-provided passwords. When an entered password succeeds, it is immediately cached into StatementPasswordCache (indexed by account_mask, sender_email, and a tenant-level fallback) so future uploads of the same statement type unlock automatically without repeated prompting.
  2. Cached Passwords: Securely stores previously working passwords mapped by account_mask (most specific, per-card) or sender_email (per-bank), falling back to all successful tenant passwords.
  3. User Profile Candidates: Standalone candidate generation from profile metadata:
    • PAN: Standard Indian PAN (both uppercase and lowercase).
    • Name+DOB: [First 4 Alpha of Name] + [DDMM] / DDMMYY / DDMMYYYY across casing variations.
    • Mobile+DOB: [Last 5 digits of Mobile] + [DDMMYY] (e.g. SBI Credit Cards).
    • Name+Account Mask: [First 4 Alpha of Name] + [Last 4 Account Digits].
    • Pure Date Formats: DDMMYYYY, DDMMYY, DDMM.
  4. Manual Retry & Partial-Unlock Continuity: If automated trials fail, the statement is saved in a PENDING state. When retried (POST /finance/statements/{id}/reprocess), if decryption succeeds and saves the unlocked PDF into Vault even when downstream parsing fails, the endpoint returns structured partial_success (unlocked: true, parsed: false) so the UI surfaces both the unlocked Vault PDF and the parse diagnostic.
  5. Idempotency & Retry Loop Suppression: Periodic automated background IMAP sync (source="EMAIL") checks existing records and immediately skips PDFs already marked FAILED (e.g. corrupt or unsupported schema), avoiding endless 3-hour retry storms while preserving full user control over manual /reprocess retries.

3. Parsing & Extraction ​

  • Heuristics: Uses native in-memory PyMuPDF (fitz.open(stream=pdf_bytes)) to verify financial keywords (balance, credit, debit, folio, isin, etc.) on incoming PDF buffers without writing temporary files to disk or requiring heavy external extractors in the Backend.
  • Normalization: Pluggable handlers (MutualFundCasHandler, BankStatementHandler) and ExternalParserService normalize bank/card/eCAS layouts into read-only StatementTransaction records across supported banks (HDFC, ICICI, Slice, Bank of Baroda). Specialized handler errors are caught and persisted cleanly as FAILED.
  • Modern Engine Upgrades: Mutual Fund CAS and AMC SOA statements are parsed using casparser 1.x (pypdfium2 engine) and PyMuPDF, providing native CAMS, KFintech, CDSL, and NSDL support without legacy 0.8.x monkey-patching.

4. Storage, Vaulting & Self-Healing ​

  • Persistent Storage (VAULT_STORAGE_PATH): Statements are persisted under /data/vault/<tenant_id>/statements/<doc_id>/vN in Docker (or <workspace>/data/vault locally) once unlocked (or as encrypted v1 while PENDING). Extracted StatementTransaction rows are immutable/read-only.
  • SHA-256 Deduplication: _ensure_vault_document compares incoming PDF SHA-256 digests against the active Vault file before uploading, preventing v2..vN duplicate version proliferation on repeated retries or email re-scans.
  • Resilient Resolution & Auto-Unlock: VaultService.resolve_file_path resolves across legacy/ephemeral roots (/data/vault <-> /app/data/vault <-> data/vault), statements/ vs. root layouts, and surviving earlier versions. VaultService.heal_legacy_paths runs automatically on backend startup, VaultService.ensure_unlocked_pdf decrypts legacy encrypted PDFs in-place on access, and VaultService.get_documents lazily backfills thumbnails for unlocked PDFs while skipping encrypted ones.
  • Data Model:
    • Statement: Metadata (filename, statement_type, account_id, vault_id, status, is_attended, closed_at, email_sender, failure_reason) supporting full statement-level CRUD.
    • StatementTransaction: Read-only extracted line items awaiting reconciliation.

5. Categorization, Reconciliation & Attendance Lifecycle ​

  • Categorization: Uses rule-based category matching (TransactionService.get_suggested_category) and dynamic read-time MerchantAlias resolution.
  • Fuzzy Matching: Transactions are matched against existing ledger entries using ref ID or a ±4-day date window, exact signed amount, and matching account.
  • Mutual Fund Portfolio Import: POST /{id}/reconcile-cas ingests selected mutual fund transactions into MutualFundHolding and MutualFundOrder, recalculating holding balances with exact mathematical precision.
  • Attendance & Review Lifecycle:
    • Hidden by Default: By default, GET /api/v1/finance/statements is queried with is_attended=false, ensuring attended statements remain hidden on initial load across both Web and Mobile apps.
    • Toggle Control (Show Attended ↔ Showing Attended): When flipped active, clients omit or pass is_attended=undefined, allowing users to inspect all statements (both attended and unattended).
    • Real-Time State Reconcile & Auto-Advance: Marking a statement attended via PATCH /{id}/attend immediately removes it from local active arrays when the attended filter is disabled. The Web UI auto-advances inspector selection to the next statement, and the Mobile app decrements total statement counters in real time.
    • Statements can be explicitly marked as attended via PATCH /{id}/attend, setting is_attended=true and stamping closed_at.
    • When attended, operational actions (Edit, Reprocess, Import, Reconcile) and transaction checkboxes are disabled to prevent accidental state mutation.
    • Individual transactions are not marked as imported by attendance; only genuinely imported/reconciled entries display ✓ Imported (CAS) or ✓ Matched (Bank). Unreconciled entries on attended statements display neutral Unimported or Unmatched badges.
    • If a statement is attended with remaining unreconciled items, an alert banner displays the exact unreconciled count.
    • Attended statements can be seamlessly reopened at any time via the Reopen button.
  • Client-Side Ingestion Hardening: The Statements interface employs request sequence tracking (statementSelectSeq & attachmentLoadSeq) and immediately clears stale table state upon switching statements, eliminating out-of-order response clobbering and visual flicker.

API Endpoints (/api/v1/finance/statements) ​

  • GET /: List statements with pagination, search, status (PARSED | PENDING | FAILED), statement_type, and is_attended filters.
  • GET /{id}: Fetch a single statement record.
  • POST /upload: Manual PDF upload with optional password and account override.
  • POST /sync: Trigger background IMAP statement scan.
  • PATCH /{id}: Update statement-level metadata (filename synced to linked Vault document, statement_type, account_id with auto-reprocess/reconciliation on FAILED statements).
  • PATCH /{id}/attend: Mark a statement as attended or reopened, toggling is_attended and setting closed_at.
  • DELETE /{id}: Soft-delete a statement & its transactions (delete_vault_file=true cleans up unreferenced Vault PDFs; create_ignore_rule=true blocks future emails from that sender).
  • POST /bulk-delete: Batch delete multiple statements with optional Vault cleanup and sender ignore rule creation.
  • POST /{id}/ignore: Create a STATEMENT ignore rule (sender | subject | pattern) and optionally clean up other matching PENDING/FAILED statements (preserving PARSED records).
  • POST /{id}/reprocess: Retry decryption/parsing with an optional manual password (preserves original email_sender).
  • POST /{id}/reconcile & POST /{id}/reconcile-cas: Run bank ledger matching or Mutual Fund portfolio import.
  • GET /{id}/transactions: View read-only extracted items.
