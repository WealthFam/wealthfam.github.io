Technical Specification: Mutual Fund CAS & AMC Statement Ingestion ​

Document Version: 1.2.0
Status: Active / Technical Reference
Owner: Investment Engineering

1. Overview ​

The Mutual Fund ingestion pipeline processes two distinct categories of investment documents in the WealthFam ecosystem:

  1. Consolidated Account Statements (CAS): Periodic aggregate statements from CAMS, KFintech, CDSL (eCAS@cdslstatement.com, cdslindia, "Central Depository Services"), and NSDL containing high-density portfolio summaries across multiple folios, fund houses, and depositories.
  2. Individual AMC Statements of Account (SOA): Folio-level statements downloaded directly from individual AMC websites or mobile apps (e.g., Nippon India MF, ICICI Prudential MF, SBI MF, Axis MF, Mirae Asset).

This document specifies the forensic extraction, fallback hierarchy, and ledger deduplication logic.

3. Data Extraction Logic ​

3.1 PDF Decryption, Vault Storage & CDSL Hardening ​

CAS and AMC files are secured with a combination of PAN and Date of Birth (DOB) or pure uppercase/lowercase PAN (or PIN code / Folio number as fallback).

  • Auto-Trial & Cache: The system attempts decryption using StatementPasswordService and user profile metadata (PAN/DOB) before marking the statement PENDING for manual input.
  • Persistent Vault Storage & Auto-Unlock: Unlocked PDFs are stored persistently under VAULT_STORAGE_PATH (/data/vault) with SHA-256 deduplication preventing duplicate version growth across retries. Legacy encrypted statement PDFs on disk are automatically unlocked in-place upon access via VaultService.ensure_unlocked_pdf.
  • casparser 1.x Native pypdfium2 Engine: Migrated casparser pin to 1.4.1+ leveraging native pypdfium2 rendering and extraction. Parser/core/utils.py (patch_casparser()) configures native pypdfium2 CAMS/KFintech/NSDL/CDSL parsing with safe decimal wrappers and fallback CDSL detection. All legacy 0.8.x monkey-patching of casparser.process has been completely purged.
  • Zero Legacy Monkey-Patches & Deprecated Flag Removal: Removed deprecated force_pdfminer: True and all 0.8.x module patching across parser callers, eliminating technical debt and deprecation warnings.
  • Tightened Handler Routing: MutualFundCasHandler.can_handle() applies word-bounded regex (r'\bcas\b', r'\bcams\b', r'\bkfintech\b', r'\bsoa\b', r'statement\s*of\s*account', r'consolidated\s*account\s*statement') and explicit negative checks for bank/credit card/cashback files.
  • Structured Error Visibility: Non-200 responses from /v1/ingest/cas are logged with full tracebacks and returned as structured error dictionaries (status, message, detail), preventing silent None drops and generic "Unknown Error" reports.

3.2 Individual AMC Statement of Account (SOA) Support ​

Single-fund statements downloaded directly from fund portals lack the SEBI-mandated investor block expected by casparser, causing Pydantic validation errors (investor_info Input should be a valid dictionary). To support direct AMC statement uploads without forcing users to request CAMS/KFintech CAS mailbacks:

  • AmcSoaParser Fallback & Password-Aware Detection: If casparser fails or if the document is recognized as a single-fund statement, execution delegates directly to AmcSoaParser. Crucially, AmcSoaParser.can_handle(file_bytes, password=password) authenticates encrypted PDFs with the provided password (and uppercase/lowercase PAN variants) before inspecting page text, avoiding fitz.FileDataError decryption exceptions.
  • Three Specialized RTA Layout Engines:
    1. KfintechSingleRowSoaParser (Nippon India, Axis MF, legacy KFintech): Parses single-row transactions where Date, Description, Net Amount, NAV, Units, and Balance are on a unified line with stamp duty embedded in parenthetical notes: $$\text{Date} \quad\vert\quad \text{Transaction Type} \quad\vert\quad \text{Amount} \quad\vert\quad \text{NAV} \quad\vert\quad \text{Units} \quad\vert\quad \text{Balance Units}$$
    2. KfintechMultiRowSoaParser (Quant MF, Groww MF, modern KFintech): Parses modern multi-row 3-line statements where each purchase/redemption spans multiple distinct table rows:
      • Row 1: Gross Purchase (or Gross Redemption)
      • Row 2: Stamp Duty @ 0.005 % (or STT Paid)
      • Row 3: Net Purchase (the execution line containing Amount, Units, NAV, and Price)
      • Visual Block Parsing & Mathematical Metric Resolution: Employs PyMuPDF block stream analysis with metric pairing: $$\text{Amount} \approx \text{Units} \times \text{NAV} \quad (\Delta < \text{₹}10.0)$$ Automatically distinguishes invested Amount (largest value), execution NAV (4 decimal places), and Units (3 decimal places) across both 5-column (Groww) and 9-column (Quant) tabular layouts.
    3. CamsSoaParser (HDFC MF, ICICI Prudential, SBI MF, Kotak Mahindra, DSP, etc.): Parses CAMS-serviced single-folio statements, extracting standard CAMS tabular structures: $$\text{Date} \quad\vert\quad \text{Description} \quad\vert\quad \text{Amount} \quad\vert\quad \text{Units} \quad\vert\quad \text{Price/NAV} \quad\vert\quad \text{Balance Units}$$
  • Canonical Normalization: Extracts Folio, Scheme Name, ISIN (regex INF[A-Z0-9]{9}), and exact transaction rows with high-precision Decimal amounts.

3.3 Smart Target User Resolution ​

Statements received via email sync often arrive on behalf of different family members within the same household:

  1. Existing Folio Ownership: In cas_handler.py, the system checks whether active MutualFundOrder records for the extracted folio already exist under a specific family member in the tenant. If found, all transactions are attributed to that user.
  2. Context Matching: If the folio is brand new, the system scans the statement text and email body for user full names and email addresses.
  3. Owner Fallback: Defaults to the tenant owner only if no user match is found.

4. Deduplication Strategy ​

Investment statements are cumulative (often spanning 6–36 months of transaction history). To prevent duplicate orders and doubled unit counts:

  1. Folio Normalization (_normalize_folio):

    • CAMS/KFintech CAS files format folios with check-digit or sub-account suffixes (e.g., '477326559824 / 0', '12345678 / 90'), whereas direct AMC statements omit the suffix ('477326559824').
    • The deduplicator normalizes folios via re.sub(r'\s*/\s*0*$', '', folio) and collapses whitespace before equality checks, ensuring CAS imports and AMC SOA imports match cleanly.

  2. Tenant-Level Multi-Member Deduplication:

    • A mutual fund folio number is globally unique to an individual account holder.
    • MutualFundService.check_duplicates checks candidate active orders across the entire household/tenant for matching (scheme_code, date, units, amount, normalized_folio).
    • Matching orders are flagged with is_duplicate: true (pre-unselected in the UI with a Duplicate badge).
    • If the statement transaction was initially unassigned, it automatically adopts the existing order's user_id.

  3. Synthesized Balance Deduplication:

    • For summary CAS statements lacking detailed transaction history, synthesized balance records are checked against existing MutualFundHolding units. If existing holding units $\ge$ incoming units, the synthesized transaction is flagged duplicate to prevent unit inflation.

  4. External Reference & Idempotency:

    • When present, normalized bank UTR / external reference IDs prevent duplicate order insertion during ledger reconciliation.

5. The "Ironclad" Ledger Standard ​

WealthFam enforces a non-destructive, "In-Place Update" policy for mutual fund data.

5.1 In-Place Updates vs. Destructive Sync ​

  • Standard Sync: Traditional apps delete all previous transactions and re-import the CAS. This breaks UUID links to goals, notes, and historical XIRR snapshots.
  • WealthFam Sync: We perform a Surgical Diff. Only new transactions are appended, and existing transactions are updated only if their fundamental metadata (Units/NAV) has changed.

5.2 Precision Calculation ​

Every calculation in the investment ledger uses the Decimal library to 6+ decimal places.

  • Zero Drift: This ensures that "Units × NAV" always matches the "Current Value" exactly, preventing the cent-level rounding errors common in mobile apps.

6. XIRR & Performance Tracking ​

XIRR (Extended Internal Rate of Return) is calculated per fund and per folio.

  • Cash Flow Verification: Returns are only calculated on "Confirmed" cash flows (Buy/Sell/Dividend).
  • Pending Status: Transactions from a CAS that do not match existing bank withdrawals are flagged for "Cash Flow Reconciliation" in the UI.
