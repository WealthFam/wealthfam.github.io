Technical Specification: Mutual Fund CAS Ingestion ​

Document Version: 1.0.0
Status: Draft / Technical Reference
Owner: Investment Engineering

1. Overview ​

The Consolidated Account Statement (CAS) ingestion pipeline is the most complex data stream in the WealthFam ecosystem. Unlike standard bank statements, CAS files from CAMS, KFintech, CDSL (eCAS@cdslstatement.com, cdslindia, "Central Depository Services"), and NSDL contain high-density investment data spanning multiple folios, depository accounts, fund houses (AMCs), and asset classes. This document specifies the forensic extraction and ledger reconciliation logic.

3. Data Extraction Logic ​

3.1 PDF Decryption, Vault Storage & CDSL Hardening ​

CAS files are universally encrypted with a combination of PAN and Date of Birth (DOB) or pure uppercase/lowercase PAN.

  • Auto-Trial & Cache: The system attempts decryption using StatementPasswordCache and user profile metadata (PAN/DOB) before marking the statement PENDING for manual input.
  • Persistent Vault Storage & Auto-Unlock: Unlocked CAS PDFs are stored persistently under VAULT_STORAGE_PATH (/data/vault) with SHA-256 deduplication preventing duplicate version growth across retries. Legacy encrypted statement PDFs on disk are automatically unlocked in-place upon access via VaultService.ensure_unlocked_pdf.
  • casparser CDSL & Header-Window Patching: Parser/core/utils.py (patch_casparser()) idempotently patches both casparser.process.process_cas_text and the imported casparser.parsers.process_cas_text binding used by read_cas_pdf() to route FileType.CDSL alongside FileType.NSDL, widen CAS type/header detection to text[:5000], and retry HeaderParseError on cover-page headers past character 1000.

3.2 ISIN & Folio Mapping ​

Mutual funds are identified using ISINs (International Securities Identification Numbers) rather than fund names to prevent "Naming Drift" (where different banks use slightly different names for the same fund).

  • Folio Consolidation: The system aggregates transactions across different AMCs into a single unified view while maintaining the original folio number for audit trails.

4. The "Ironclad" Ledger Standard ​

WealthFam enforces a non-destructive, "In-Place Update" policy for mutual fund data.

4.1 In-Place Updates vs. Destructive Sync ​

  • Standard Sync: Traditional apps delete all previous transactions and re-import the CAS. This breaks UUID links to goals, notes, and historical XIRR snapshots.
  • WealthFam Sync: We perform a Surgical Diff. Only new transactions are appended, and existing transactions are updated only if their fundamental metadata (Units/NAV) has changed.

4.2 Precision Calculation ​

Every calculation in the investment ledger uses the Decimal library to 6+ decimal places.

  • Zero Drift: This ensures that "Units × NAV" always matches the "Current Value" exactly, preventing the cent-level rounding errors common in mobile apps.

5. XIRR & Performance Tracking ​

XIRR (Extended Internal Rate of Return) is calculated per fund and per folio.

  • Cash Flow Verification: Returns are only calculated on "Confirmed" cash flows (Buy/Sell/Dividend).
  • Pending Status: Transactions from a CAS that do not match existing bank withdrawals are flagged for "Cash Flow Reconciliation" in the UI.

6. Deduplication Strategy ​

CAS files are cumulative (often containing 6-12 months of history). To prevent duplication:

  1. MD5 Payload Hashing: Every transaction is hashed based on (Folio, ISIN, Date, Units, Amount).
  2. Idempotency Check: If the hash already exists in the ledger, the transaction is discarded silently.
  3. Cross-Source Matching: The system identifies matches between a CAMS entry and a Bank Statement entry (e.g., a "SIP Debit" in the bank vs. a "Purchase" in the CAMS).

7. Future Enhancements ​

  • CAMS API Integration: Transitioning from PDF parsing to direct CAMS API ingestion for zero-latency sync.
  • Tax Harvesting Analysis: Real-time identification of Short Term (STCG) and Long Term (LTCG) tax implications based on FIFO (First-In-First-Out) logic.
