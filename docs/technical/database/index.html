🗄️ Database Architecture ​

WealthFam uses a dual-database design: PostgreSQL as the authoritative financial ledger and document metadata repository, and embedded DuckDB as the high-performance analytical timeseries database for Admin Studio telemetry and observability. The Parser microservice operates 100% statelessly in memory with zero tables stored at rest.

🗺️ Logical Relationship Diagram ​

WealthFam uses a strict relational structure in PostgreSQL to ensure Precision parentage of every transaction.

🏗️ Core Schemas ​

⚙️ Backend Schema ​

The primary ledger and product metadata schema in PostgreSQL:

  • High-concurrency transaction and account tables (transactions, accounts, statements).
  • Cross-source deduplication indices (content_hash, external_id).
  • Ingestion audit logs (ingestion_events, email_sync_item_logs).
  • Document Vault storage metadata (document_vault, document_versions).
  • Tenant-scoped merchant normalization rules (merchant_aliases).
  • Mutual Fund holdings and intelligence records (mutual_fund_holdings, mutual_fund_orders, mutual_fund_sips, mutual_fund_constituents, mutual_fund_benchmarks).

🔄 Stateless Parser Engine (0 Tables at Rest) ​

The Financial Parser Microservice is completely stateless. It performs zero database writes during runtime:

  • Network idempotency is secured via an in-memory 5-minute sliding LRU cache (RecentSubmissionCache).
  • Bank rules are compiled Python parsers in Parser/parsers/bank/.
  • Financial deduplication is delegated to PostgreSQL's TransactionDeduplicator.
  • Telemetry metrics are streamed asynchronously to Admin DuckDB.

🛡️ Critical Pattern: JSON/JSONB Array Handling ​

For columns storing JSON arrays (like CategoryRule.keywords), the backend uses PostgreSQL's native JSONB column type.

  • WealthFam enforces a Safe Deserialization Pattern: keywords are deserialized using a validation helper (RuleExecutor._parse_keywords), which correctly handles both Python list types and serialized JSON string types (e.g. '["KEYWORD"]') returned by the database.
  • Keyword validation and formatting are performed strictly before transactions are committed to ensure DB constraints are satisfied.

🗄️ Why this Dual-Database Design? ​

🐘 PostgreSQL (Backend) ​

PostgreSQL handles the core system ledger (transactions, accounts, statements), Document Vault metadata (document_vault, document_versions, backed on disk by persistent VAULT_STORAGE_PATH=/data/vault with automatic startup path self-healing), multi-user tenant partitioning, ingestion audit logs (ingestion_events, email_sync_item_logs storing full raw_content, outcome, and details_json), user filter rules (spam_filters covering SMS, EMAIL, STATEMENT, and ALL; plus ignored_patterns), and tenant-scoped merchant_aliases. It provides ACID concurrency, standard indices, and startup/Alembic schema management.

🦆 DuckDB (Admin Telemetry Timeseries & Control Plane) ​

DuckDB powers the Admin telemetry and observability control plane (data/telemetry.duckdb), served from the root data/ volume (/data/ in Docker):

  • Stateless Parser: The Parser microservice is 100% stateless and code-driven using compiled Python parsers and an in-memory thread-safe submission cache (RecentSubmissionCache). It does not persist financial PII or write request logs to disk, completely eliminating DuckDB lock contention during high-concurrency ingestion batches. Scrubbed extraction metrics are shipped asynchronously to Admin-Backend.
  • Admin Telemetry (telemetry.duckdb): Anonymous API latency percentiles (telemetry_api_metrics), parser extraction telemetry (telemetry_parser_events), mobile/web client telemetry (telemetry_client_events), PII-scrubbed logs (telemetry_system_logs), 30s health probes (endpoint_health_checks), consented format-preserved telemetry_training_samples, and admin_users.
  • Brand Assets (data/logos/ + PostgreSQL brand_logos): Individual brand icon files reside in data/logos/ while metadata and matching regexes live in PostgreSQL (brand_logos with an offline DuckDB mirror).
*Precision Ledger · Columnar Performance · Privacy First*
