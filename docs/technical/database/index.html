🗄️ Database Architecture ​

WealthFam uses a dual-database architecture. It uses PostgreSQL for the core backend database (relational ledger and high-concurrency balance sheets) and DuckDB for the parser service (ingestion logs and pattern-matching tables). Below are the core schema definitions used across the ecosystem.

🗺️ Logical Relationship Diagram ​

WealthFam uses a strict relational structure in PostgreSQL to ensure Precision parentage of every transaction.

🏗️ Core Schemas ​

⚙️ Backend Schema ​

The primary ledger and product metadata schema.

  • High-concurrency transaction tables.
  • Multi-member family partitioning.
  • Precision audit trail structures.

🔄 Parser Schema ​

The transient ingestion and pattern-matching schema.

  • Raw message hashing.
  • Regex pattern templates.
  • Deduplication metadata.

🛡️ Critical Pattern: JSON/JSONB Array Handling ​

For columns storing JSON arrays (like CategoryRule.keywords), the backend uses PostgreSQL's native JSONB column type.

  • WealthFam enforces a Safe Deserialization Pattern: keywords are deserialized using a validation helper (RuleExecutor._parse_keywords), which correctly handles both Python list types and serialized JSON string types (e.g. '["KEYWORD"]') returned by the database.
  • Keyword validation and formatting are performed strictly before transactions are committed to ensure DB constraints are satisfied.

🗄️ Why this Dual-Database Design? ​

🐘 PostgreSQL (Backend) ​

PostgreSQL handles the core system ledger. It allows for reliable multi-user transactions, concurrent writes without locking (migrated away from single-writer constraints), standard indices, and robust schema changes with Alembic.

🦆 DuckDB (Parser Ingestion DB & Admin Telemetry Timeseries) ​

DuckDB powers both the Parser microservice (data/ingestion_engine_parser.duckdb) and the Admin telemetry control plane (data/telemetry.duckdb), served from the root data/ volume (/data/ in Docker):

  • Parser Ingestion (ingestion_engine_parser.duckdb): Pattern matching rules, merchant aliases, and request logs.
  • Admin Telemetry (telemetry.duckdb): Anonymous API latency percentiles (telemetry_api_metrics), parser extraction telemetry (telemetry_parser_events), mobile/web client telemetry (telemetry_client_events), PII-scrubbed logs (telemetry_system_logs), 30s health probes (endpoint_health_checks), non-destructive parser_templates, consented telemetry_training_samples, and admin_users.
  • Brand Assets (data/logos/ + PostgreSQL brand_logos): Individual brand icon files reside in data/logos/ while metadata and matching regexes live in PostgreSQL (brand_logos with an offline DuckDB mirror).
*Precision Ledger · Columnar Performance · Privacy First*
