SMS Flow & Ingestion Architecture ​

This document describes the high-fidelity, resilient SMS ingestion and synchronization pipeline for the WealthFam Mobile App (Android) and its integration with the backend ingestion engine.

Architecture Overview ​

The Mobile App serves as the primary real-time financial telemetry sensor. It employs a four-stage fault-tolerant pipeline ensuring 100% message throughput, zero lost transactions, process-safe deduplication, and precise GPS location telemetry even when the app is killed, the device is rebooted, or the network is offline.

1. Native Interception Layer (SmsReceiver.kt) ​

The entry point for all incoming SMS messages is a native Android BroadcastReceiver configured in AndroidManifest.xml with maximum priority:

xml
<receiver android:name=".SmsReceiver"
    android:permission="android.permission.BROADCAST_SMS"
    android:exported="true">
    <intent-filter android:priority="999">
        <action android:name="android.provider.Telephony.SMS_RECEIVED" />
    </intent-filter>
</receiver>

Key Native Capabilities ​

  1. Multi-Part SMS Reconstruction: Long SMS messages delivered as split PDUs are aggregated by originating address before processing:

    kotlin
    val groupedBodies = linkedMapOf<String, StringBuilder>()
for (sms in messages) {
    val sender = sms?.displayOriginatingAddress ?: "Unknown"
    val body = sms?.displayMessageBody ?: ""
    groupedBodies.getOrPut(sender) { StringBuilder() }.append(body)
}

  2. Smart On-Device OTP Filtering: Pure two-factor authentication / login OTPs (e.g. Google or WhatsApp login codes) are filtered out on-device, saving battery and eliminating non-financial noise. However, OTPs containing transaction indicators (debited, spent, acct, avl bal, purchase, refund) are preserved and ingested:

    kotlin
    private fun isPureOtpMessage(body: String): Boolean {
    return otpPattern.containsMatchIn(body) && !transactionPattern.containsMatchIn(body)
}

  3. Multi-Tiered GPS Location Resolution: To tag transactions with geolocation metadata without blocking the broadcast receiver thread or draining battery:

    • Hardware/System Provider: Queries LocationManager.FUSED_PROVIDER on Android 12+ (API 31+), with fallback to NETWORK_PROVIDER, PASSIVE_PROVIDER, and GPS_PROVIDER.
    • Flutter SharedPreferences Decoding: When hardware location is cold or disabled, falls back to the app's cached coordinates in FlutterSharedPreferences. Handles Flutter's Android shared_preferences base64 string prefix (VGhpcyBpcyB0aGUgcHJlZml4IGZvciBEb3VibGUu) as well as explicit string doubles (cached_gps_lat_str, cached_gps_lng_str).

  4. Zero-Service Start Constraint: Instead of calling startForegroundService directly from the broadcast receiver (which triggers ForegroundServiceStartNotAllowedException on Android 12 through 16), SmsReceiver.kt writes atomic JSON files directly into context.filesDir/sms_relay/. This decouples SMS capture from the Flutter engine lifecycle.

2. Background DataSync Layer (foreground_task_handler.dart) ​

Background message dispatch is orchestrated by flutter_foreground_task running as an independent background isolate under ForegroundServiceTypes.dataSync.

  • 15-Second Heartbeat: The isolate executes onRepeatEvent() every 15 seconds to sweep the files/sms_relay/ directory.
  • Background Location Caching: If Geolocator.getLastKnownPosition() resolves fresh coordinates in the background isolate, it immediately writes them back to cached_gps_lat and cached_gps_lat_str so that subsequent SMS retain valid coordinates.
  • Offline Resiliency: If credentials are missing, the server is unreachable, or an expired JWT returns HTTP 401, messages are safely written to sms_offline_queue in SharedPreferences with preserved timestamps and GPS telemetry.
  • Process Communication: Emits sms_synced and sms_queued events across isolate communication ports to keep the main UI updated without polling.

3. Main App Service Layer (sms_service.dart) ​

SmsService coordinates manual synchronization, background isolate configuration, deduplication, and store-and-forward retry mechanisms.

GPS Warm-Up & Resolution Chain ​

On app initialization, init() calls getCurrentOrCachedLocation() to warm up GPS hardware and populate SharedPreferences (cached_gps_lat, cached_gps_lng, cached_gps_lat_str, cached_gps_lng_str).

When a transaction is queued or sent:

  1. Checks explicit coordinates provided in payload.
  2. Checks in-memory and persistent metadata (sms_metadata_store).
  3. Queries Geolocator.getLastKnownPosition() or low-accuracy getCurrentPosition with a 4-second timeout.
  4. Falls back to globally cached SharedPreferences coordinates.

Deduplication Engine ​

To prevent duplicate financial records across multiple sync attempts, network retries, or manual inbox scans:

  • Normalization: Senders and bodies are stripped of non-alphanumeric characters and lowercased.
  • Hour-Level Window: Timestamps are coerced to hour-level resolution (YYYYMMDDHH) to absorb network transmission and carrier latency.
  • Cryptographic Hash: SHA-256(cleanAddress-cleanDate-cleanBody).
  • Append-Only Journal: Synced hashes are recorded in files/synced_hashes.db for thread-safe cross-process persistence alongside sms_hash_<hash> SharedPreferences flags.

Store-and-Forward Retry Queue ​

All SMS items are committed to sms_offline_queue before network transmission. Retries are triggered by:

  • Dynamic connectivity listeners (Connectivity().onConnectivityChanged).
  • 15-second periodic retry timers (_retryTimer).
  • App resume and manual pull-to-refresh (syncNow()).
  • WebSocket reconnection events.

4. Backend Ingestion Contract ​

All SMS payloads are transmitted to the backend ingestion router:

Endpoint ​

POST /api/v1/ingestion/sms

Request Payload (SmsPayload) ​

json
{
  "sender": "HDFCBK",
  "message": "Rs 450.00 debited from A/C **1234 on 11-NOV-26 at SWIGGY. Avl Bal Rs 12,450.50",
  "date": 1762867200000,
  "received_at": "2026-11-11T14:40:00Z",
  "hash": "a8f3b...4c2",
  "device_id": "9a8b7c6d-...",
  "latitude": 12.9716,
  "longitude": 77.5946,
  "lat": 12.9716,
  "lng": 77.5946
}

Backend Processing ​

  1. Device Tracking: Updates the device's last_seen_at timestamp.
  2. External Parser: Parses raw SMS body into structured transaction items (amount, type, merchant, category, account_mask, ref_id, balance).
  3. Location Attachment: In IngestionService.process_transaction, extra_data (latitude, longitude, device_id) is saved onto the database Transaction model.
  4. Interactive Map Display: When viewed in TransactionDetailScreen, transactions containing coordinates render an interactive OpenStreetMap via FlutterMap.

5. Debug Mode & Telemetry (SmsDebugLogsScreen) ​

When Debug Mode (AppConfig.sendDebugPayload) is active:

  • Every SMS sync attempt (success or failure) across both the foreground service and main app isolate is logged to sms_debug_logs.
  • Logs include HTTP response codes, response bodies, error messages, execution source (Direct Send, Background ForegroundService, Offline Queue), and raw payload JSON.

Screen Features ​

  • One-Touch Toggle: Enable or disable Debug Mode directly from the top card of SmsDebugLogsScreen.
  • Telemetry Badges:
    • 🟢 📍 12.971, 77.594 when GPS is present.
    • 🟠 ⚠️ No GPS if coordinates were missing.
    • HTTP 200, HTTP 500, or ERR status badges.
  • Developer Tools: 1-tap Copy Payload to clipboard and Clear Debug Logs action in the AppBar.
