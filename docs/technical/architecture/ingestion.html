📥 Precision Data Ingestion Flow ​

WealthFam features a sophisticated, multi-channel ingestion pipeline designed to minimize manual entry while maintaining 100% data accuracy through idempotent hashing and tiered parsing logic.

⚡ Multi-Channel Ingestion ​

Our system captures data from three primary streams:

  1. Mobile SMS Ingestion: Real-time capture of bank transaction alerts directly from Android background listeners.
  2. Email IMAP Sync: Periodic scanning of authorized email accounts for bank statements and CAMS PDFs.
    • Automated Statement Capture: Automatically identifies, downloads, and pre-processes bank statement PDFs (e.g., HDFC, Swiggy HDFC) from incoming emails.
  3. Manual Web Ingestion: High-fidelity bulk uploads via CSV, Excel, or PDF files through the desktop dashboard.

🏗️ The Pipeline Lifecycle ​

🏦 CAMS/KFintech & Investment Ledger ​

Our investment sync handles the complex extraction from bank-issued PDFs and enforces an Ironclad Precision Standard for the life of the asset.

For a deep-dive into the CAMS/KFintech extraction logic, see the CAS Ingestion Technical Specification.

The Hardened Ledger Principles ​

  1. Identity Preservation: Unlike traditional systems that delete and recreate holdings during a sync, WealthFam performs In-Place Updates. This preserves the internal UUID of your holdings, ensuring that your linked Investment Goals, historical charts, and frontend caches never break (Zero 404 Resilience).
  2. Absolute Decimal Precision: Every NAV, unit count, and cost-basis calculation is performed via Python's Decimal library. This eliminates the "Floating Point Drift" common in financial apps, where rounding errors accumulate over hundreds of SIP transactions.
  3. Non-Destructive Management (Soft-Delete): Manual cleanup of "junk" data or correction of duplicate CAMS entries is non-destructive. Transactions are marked with is_deleted, allowing for a full audit trail and the ability to "un-delete" historical data.

The 'What-If' Impact Analysis ​

When a user attempts to surgically delete a transaction or a folio, the system invokes the Predictive Projection Engine:

  • Step 1: It creates a transient, in-memory clone of the holding's order history.
  • Step 2: It applies the proposed deletion to the clone.
  • Step 3: It re-executes the IRR and Average Cost algorithms on the transient data.
  • Step 4: It broadcasts the delta (e.g., "Profit will drop by ₹540, XIRR will rise to 14.2%") to the UI before the user commits the change.

🛡️ Key Technical Features ​

1. Idempotency (MD5 Hashing) ​

Every ingestion attempt generates a unique hash based on the raw payload, timestamp, and source metadata. This ensures that the same SMS or email is never processed twice, even if the sync service restarts.

2. Tiered Parsing Logic ​

To maximize speed and minimize costs, we use a tiered approach:

  • Tier 1 (Static): Hardcoded templates for major banks (HDFC, ICICI, etc.).
  • Tier 2 (Heuristics): Algorithmic identification of currency, amounts, and vendors.
  • Tier 3 (AI Fallback): Real-time inference using Gemini Pro for highly complex or non-standard messages.

3. Precision Deduplication ​

Beyond simple IDs, WealthFam uses "Fuzzy Time-Windowing" to identify duplicate transactions across different sources (e.g., an SMS alert and a bank statement entry for the same coffee purchase).

4. Bank Statement Ingestion & Automation ​

WealthFam supports bulk ingestion of bank statements (PDF/CSV) with automated classification rule generation.

For a detailed architectural breakdown of the PDF parsing algorithm, see the Statement Ingestion Deep Dive.

  • Deep Table Parsing: Specialized parsers (e.g., swiggy_hdfc.py) extract data from complex bank PDF layouts.
  • Automated Rule Generation: During ingestion, users can opt to save a classification rule based on the transaction's description.
  • Session Isolation (Persistence Hardening): To prevent data corruption during bulk operations, rules are "expunged" from the active database session after creation. This ensures that the Python-level object state (e.g., list of keywords) does not conflict with the database's storage format (e.g., JSON strings) during secondary commits.

🛠️ Deep How-To: Troubleshooting Ingestion ​

If a transaction from an SMS or Email fails to appear in your ledger:

Step 1: Inspect the Unified Ingestions Feed ​

  1. Navigate to Settings → Ingestions (GET /api/v1/ingestion/activity, default range Today).
  2. Filter by Source (SMS / EMAIL), Person, Device / Mailbox, Account, Outcome, or Search, and click View Content to read the exact message body.
  3. Follow the plain-English outcome CTA:
    • blocked_unlinked_account → Link the missing account mask in Accounts.
    • moved_to_triage → Assign or confirm the category in Categories → Category Rules.
    • ignored_by_rule → Click Allow if a user ignore rule blocked a legitimate message.

Step 2: Check Pre-Extraction Filtering & Deduplication ​

  • User ignore rules (SpamFilter / IgnoredPattern) run in Backend via IngestionService.check_ignore_rules() before calling Parser.
  • Promotional and OTP emails are filtered strictly by FinancialClassifier.is_financial(..., source="EMAIL") and structured email bank parsers without loose fallback fabrication.

Step 3: Submit Anonymized Samples & Tune Rules (Operators) ​

  1. End users seeing unrecognized_alert in Settings → Ingestions (or Mobile → Ingestions) can preview PII masking and submit a consented sample via POST /api/v1/ingestion/anonymize-preview and POST /api/v1/ingestion/report-unrecognized (proxied to settings.ADMIN_API_V1_URL).
  2. Operators inspect incoming samples, test templates in the sandbox, and manage regex patterns in Admin-Web → Parser Studio (Port 8080 / :5174).

🏛️ Separation of Concerns: Consumer Invisibility vs. Dedicated Operations Portal ​

A core architectural tenet of WealthFam is that a consumer end-user should never see internal parser concepts, regexes, or parser microservice routes.

  1. Consumer Experience (Web-App & Mobile-App):

    • Zero /parser proxies (parserClient/parserApi and ParserSettings.vue removed); consumer apps talk only to Backend (:8000).
    • Ingestion surfaces through plain-English Ingestions activity feeds displaying full SMS/Email content, outcomes, Ignore / Allow controls, and PostgreSQL-backed Merchant Aliases under Categories & Rules.
    • Ground-Truth Reconciliation: Reconciling statement lines automatically promotes matching items in PendingTransaction triage into approved ledger entries without duplicate key rejections or NoneType crashes.
    • PostgreSQL JSONB Compatibility: Classification rules generated from statement descriptions use cast(keywords, String).ilike() for full cross-database compatibility.

  2. Dedicated Operations Portal (Admin-Backend & Admin-Web):

    • Internal parser debugging, built-in parser introspection, template CRUD, sandbox testing, training inbox, brand logos, and telemetry reside exclusively in the port-isolated admin console (:8002 / :8080).
