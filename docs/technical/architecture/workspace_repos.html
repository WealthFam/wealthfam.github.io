WealthFam Ecosystem: The Architectural Manifesto ​

This document provides an exhaustive reference for the WealthFam multi-repository workspace. It is the primary training data for AI agents and the transition guide for human architects.

1. Repository Taxonomy & Governance ​

The workspace is divided into Source Repositories (logic owners) and Operational Repositories (deployment & testing).

2. Technical Philosophy & Core Patterns ​

2.1 The "Ironclad" Transaction Pattern ​

With the migration to PostgreSQL as the core backend storage, database interactions support native ACID transaction management:

  • ACID Concurrency: Thanks to PostgreSQL's native transaction isolation and concurrency support, standard write operations do not require any application-level write locks. The custom db_write_lock is no longer used in the backend.
  • Atomic Snapshots: When a financial balance is updated, the system automatically creates a BalanceSnapshot entry. This allows for historical auditing and "Time Machine" financial views without recalculating thousands of transactions.

2.2 Tenant Isolation & Security ​

WealthFam is built on a Multi-Tenant Architecture:

  • Tenant ID: Every table (except system-wide metadata) contains a tenant_id column.
  • JWT Scoping & Vault Seal Guard: Authentication tokens include the tenant_id. get_current_user filters all queries by the user's tenant and verifies KeyRingService.is_unsealed(tenant_id) in strict mode, returning HTTP 401 (code: "TENANT_SEALED") if the in-memory DEK was evicted (e.g., after a container restart) so clients cleanly prompt re-login instead of failing mid-write.
  • Password Hashing: We use bcrypt for hashing. The field name in the database is strictly password_hash.

3. Communication & Proxy Architecture ​

3.1 The "Nginx Controller" ​

In the Monolith Docker & Demo (Render IO) deployments, Nginx acts as the unified ingress controller with port-isolated admin routing:

  • Unprivileged Execution & Capability Hardening:
    • Standalone web frontend images (Web-App and Admin-Web) run strictly as unprivileged non-root users (USER nginx) listening internally on high port 8080.
    • No Linux file capabilities (setcap / libcap) are used. This prevents EPERM (Operation not permitted, exit status 126) failures on hardened container platforms that enforce PR_SET_NO_NEW_PRIVS=1 (such as Render, Google Cloud Run, rootless Podman, or Kubernetes clusters enforcing allowPrivilegeEscalation: false).
    • In Docker Compose, external host port 80 cleanly maps to container port 8080 (80:8080), preserving standard browser entrypoints.
  • Port 80 (Client Ingress):
    • Frontend: / → Web-App static SPA (zero direct /parser exposure).
    • API Routing: /api → Proxied to FastAPI Backend (Port 8000), which handles internal calls to Parser (PARSER_SERVICE_URL), client telemetry proxying (/api/v1/telemetry/ingest), and anonymized reporting proxies to Admin-Backend (ADMIN_SERVICE_URL).
    • WebSocket Routing: /ws/ → Proxied to FastAPI Backend WebSockets (Port 8000).
    • Telemetry Routing: /telemetry/ → Proxied to Admin-Backend write-only anonymous ingestion (Port 8002).
    • Health Checks: Monitors GET /health against the underlying backend service.
  • Mobile & Client Telemetry Ingestion Policy:
    • Web App: Flushes anonymous route navigation latencies, API error rates, and unhandled Vue exceptions via /telemetry/ingest (using sendBeacon on page unload) with explicit opt-in preference toggles.
    • Mobile App: Emits app lifecycle transitions, foreground SMS heartbeats, sync latencies, and sanitized crash signatures through the Backend proxy (/api/v1/telemetry/ingest), requiring zero secondary URL configurations. Features offline-first SharedPreferences queuing (FIFO 100 max) that retains data across network outages and retries on reconnection. Supports independent cloud hardcoding via TelemetryService.dedicatedTelemetryUrl.
  • Port 8080 (Dedicated Port-Isolated Admin Ingress):
    • Admin UI: / → Admin-Web static SPA.
    • Admin API & WebSocket Logs: /admin-api/ → Proxied to Admin-Backend (Port 8002 /v1/).

3.2 Subpath Routing Policy ​

To maintain compatibility across Localhost, Docker, and Cloud (Render), we use Relative Paths in all test and frontend calls.

  • Example: Requesting /auth/login while the base URL is https://wealthfam.com/api/v1/ will correctly resolve to /api/v1/auth/login.

4. Deployment Pipeline (The Official Demo Sync Flow) ​

IMPORTANT

This pipeline is designed exclusively for the Official WealthFam Demo hosted on Render. User deployments for personal use should follow the Local Docker pathway.

We use a "Staging Area" strategy for the official cloud demonstration:

  1. Developer modifies Source Repos (backend, parser).
  2. The sync_to_demo.sh script (in the Demo (Render IO) repo) is executed.
  3. This script wipes the local subdirectories in the Demo repo and clones/copies the fresh code from the backend, parser, and AI Agent directories.
  4. The Demo repo is then pushed to GitHub, triggering Render.io to build the multi-container environment.

5. Testing & Validation Strategy ​

The Test Suite is the ultimate truth for system health.

  • Cloud-Aware Testing: The suite detects if it is running in GitHub Actions and automatically switches to a CIClient.
  • Path Stripping: The CIClient is designed to strip leading slashes from request URLs, forcing httpx to append paths to the /api/v1 or /parser base URLs instead of replacing them. This is critical for hittingproxied subpaths.

6. Guidelines for Future AI Agents ​

  1. Stop & Search: Before refactoring a service, check the Docs/ repo for existing patterns (e.g., how to handle PostgreSQL concurrency and indexes).
  2. Edit Source First: Never apply architectural changes directly to the Demo folder. They will be lost on the next sync.
  3. Validate Locally: Run docker-compose up from the Infra repo to ensure your changes work in a containerized environment before pushing to the cloud.
  4. Update This Doc: If you change a core pattern (e.g., moving from DuckDB to Postgres), update this Manifesto immediately.

7. Documentation Engineering ​

WealthFam follows a Documentation-as-Code philosophy. Our technical documentation is treated with the same rigor as our application code.

7.1 The Docs Stack ​

  • Engine: We use VitePress to generate a fast, optimized, and SEO-friendly static site.
  • Source: All markdown files live in the Docs repository.
  • Automation:
    • Documentation is automatically rebuilt on every push to the Docs repository.
    • A GitHub Action (.github/workflows/deploy.yml) handles the build and syncs the static assets to the wealthfam.github.io repository for public hosting.

7.2 Navigation & Structure ​

  • Configuration: The sidebar and top-level navigation are managed via .vitepress/config.mts.
  • Content Types:
    • /technical/: Deep dives into backend, schema, and mobile logic.
    • /user/: End-user guides and feature walkthroughs.
    • /deployment/: Infrastructure and dev-ops instructions.
    • /Management/: Governance, RFCs, and contribution guidelines.

7.3 Guidelines for Updates ​

  • When a new microservice is added, it must be documented in this Docs repository.
  • Use internal linking (e.g., [Link](./other_doc.md)) for seamless cross-referencing.
  • Ensure all images are stored in /Media/ and referenced with absolute paths within the documentation site.
