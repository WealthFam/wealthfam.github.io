📜 RFC 0001: Modular PII, Location & Vault Encryption Architecture ​

MetadataDetails
RFC Number0001
TitleModular PII, Geolocation & Zero-Knowledge Vault Encryption
StatusImplemented
AuthorAntigravity AI & Engineering Team
Target Releasev2.2.0
Gated Backlog ItemsZero-Knowledge Vault & User-Keyed Database Encryption

1. Summary ​

Currently, WealthFam stores personal identifiable information (PII)—including user full names, email addresses, phone numbers, PAN identity numbers, transaction geolocation coordinates (latitude/longitude), statement unlock passwords, and IMAP credentials—in plaintext or static-key columns within PostgreSQL. Additionally, physical documents in VAULT_STORAGE_PATH (tax returns, payslips, statement PDFs) are stored in plaintext on disk.

If a developer, DBA, hosting provider, or malicious actor obtains a database dump (pg_dump) or server storage backup, this sensitive PII is exposed.

This RFC introduces a Modular Asymmetric Split-Envelope Encryption Architecture that guarantees:

  1. Zero Database Leakage: Direct database queries or database dumps contain only AES-256-GCM ciphertexts (enc:v1:...) and non-invertible HMAC blind indexes.
  2. Zero Disk Leakage: Stored PDFs, tax documents, and thumbnails on disk are encrypted using streaming AES-256-GCM.
  3. Decoupled & Modular Design: All cryptography is encapsulated in Backend/app/core/crypto/ via transparent SQLAlchemy custom types (EncryptedString, EncryptedJSON, EncryptedNumeric) with no cross-module coupling.
  4. Uninterrupted 24/7 Background Automations: In-memory KeyRingService holds tenant decryption keys in volatile process RAM until server restart, allowing APScheduler to fetch and parse bank emails at 3:00 AM without user interaction.
  5. High-Speed Ledger Math: Financial analytics (amount, date, category_id, balance) remain standard typed SQL columns to preserve sub-5ms aggregations (SUM, AVG, monthly sparklines).

C. Modular Implementation Components ​

To guarantee modularity and zero vendor lock-in, all encryption code resides in Backend/app/core/crypto/:

  1. keyring.py (KeyRingService):

    • Manages tenant Data Encryption Keys (DEKs) in a thread-safe, volatile memory cache.
    • Provides unseal_tenant(tenant_id, dek), get_tenant_dek(tenant_id), and evict_tenant(tenant_id) (emergency lock).
    • Keys are never persisted to disk or DB.

  2. blind_index.py (BlindIndexService):

    • Computes deterministic, non-reversible indexes: $$\text{bindex} = \text{HMAC-SHA256}(\text{normalize}(value), \text{BLIND_INDEX_SALT})$$
    • Normalization removes casing, spaces, and formatting before hashing to ensure exact matches work reliably (e.g., lowercase email, stripped phone).

  3. types.py (SQLAlchemy Custom Types):

    • EncryptedString, EncryptedText, EncryptedNumeric: Custom TypeDecorator subclasses.
    • Transparently handles encryption on process_bind_param (Python $\to$ DB) and decryption on process_result_value (DB $\to$ Python).
    • Backend routes and services continue using user.email or user.full_name as normal strings.

  4. vault_cipher.py (VaultFileCipher):

    • Wraps standard Python I/O streams (BufferedReader, BufferedWriter) with AES-256-GCM chunked streaming (64KB chunks).
    • Appends 12-byte initialization vector (IV) and 16-byte authentication tag per file.

D. Unattended Background Lifecycle (The Unseal / Reboot Workflow) ​

  1. Cold Boot / Server Restart:
    • The server process starts in the SEALED state (RAM empty).
    • If an automated task (e.g., APScheduler IMAP check) runs before any tenant member has logged in, it catches TenantSealedException, logs an informational message, and gracefully skips execution.
  2. First Login / Silent Mobile Token Refresh:
    • The user opens the Mobile App or Web App (or the Mobile App background task performs its periodic token sync).
    • The authentication handler unwraps the tenant's DEK and registers it into KeyRingService.
    • The tenant is now UNSEALED.
  3. Continuous Background Execution:
    • As long as the server remains running, background tasks for this tenant decrypt credentials in-memory and execute uninterrupted.
  4. Emergency Tenant Lock:
    • A user can trigger POST /api/v1/auth/lock-vault, calling keyring.evict_tenant(tenant_id) to instantly seal their data in RAM without server downtime.

E. Zero-Retention Policy for Raw Ingestion & Anonymized Training Feedback ​

1. In-Memory Parsing & Ephemeral Discard (Data Minimization) ​

Raw bank emails and SMS messages present an immense privacy risk because they often contain:

  • One-Time Passwords (OTPs) and 2FA codes.
  • Complete bank balances and credit limits.
  • Home addresses, personal notes, or unlinked communications.

Policy: Raw message text will never be saved permanently in the database.

  • Workflow:
    1. The incoming message or email is streamed directly into the in-memory parsing pipeline.
    2. The parser extracts the normalized structured financial record (amount, date, merchant, account_mask, ref_id).
    3. The structured PendingTransaction is committed.
    4. The raw email/SMS body is immediately garbage collected and discarded from memory.
    5. The legacy columns PendingTransaction.raw_message, UnparsedMessage.raw_content, and EmailSyncItemLog.raw_content will be deprecated and eliminated.

2. Opt-In Anonymized Training Feedback Flow (Parser Improvements) ​

When an SMS or bank email cannot be recognized by the parser:

  • Rather than hoarding unparsed raw messages on the server, the Mobile App or Web App UI will present an opt-in review card in the Triage Hub:

    "Unrecognized bank format detected. Would you like to share this template to help add support for this bank?"

  • Client-Side Sanitization & Scrubbing: Before any data leaves the user's device, an automated regex sanitizer aggressively scrubs all sensitive entities:
    • Numeric amounts $\to$ <AMOUNT>
    • Account numbers & cards $\to$ <CARD_XXXX>
    • Dates & timestamps $\to$ <DATE>
    • OTPs / 6-digit codes $\to$ <OTP_REMOVED>
    • Personal names & emails $\to$ <NAME_REMOVED>
    • Available balances $\to$ <BALANCE_REMOVED>
  • User Preview & Explicit Consent: The UI displays the scrubbed template to the user:
    Sent: INR <AMOUNT> spent on Card <CARD_XXXX> at <MERCHANT> on <DATE>. Avl Lmt: <BALANCE_REMOVED>
  • The user must explicitly tap "Approve & Submit Anonymized Template".
  • This guarantees continuous parser training improvements without collecting a single byte of user PII or raw message history.

F. Zero-Downtime Key Versioning & Key Rotation Specification ​

1. Explicit Ciphertext Envelope Format ​

To ensure seamless key evolution over years of operation without database lockups, all encrypted values follow a version-explicit envelope format: $$\text{enc}:\mathbf{v{N}}:\mathbf:\mathbf:\mathbf$$

  • enc: Magic header identifying ciphertext.
  • v{N}: Key Version integer (e.g. v1, v2, v3).
  • iv_hex: 12-byte (96-bit) cryptographically random initialization vector.
  • tag_hex: 16-byte (128-bit) GCM authentication tag.
  • ciphertext_hex: The encrypted payload.

2. Key Hierarchy & Tenant Key Ring Structure ​

A tenant holds an active key version and a historical keyset in volatile RAM:

python
class TenantKeyRing:
    active_version: int = 1
    keys: dict[int, bytes] = {
        1: b"...", # 256-bit AES key for v1
        2: b"...", # 256-bit AES key for v2
    }

3. Dual-Track Rotation Model (Lazy Opportunistic + Batch Background) ​

When a tenant initiates a key rotation (e.g., following a password change or security policy):

  1. A new version (v2) is generated and set as active_version.
  2. Immediate Zero-Downtime Writes: Any new or updated records immediately write with enc:v2:....
  3. Lazy Opportunistic Re-Keying: When a user reads a historical record prefixed with enc:v1:...:
    • The ORM decrypts it using key v1.
    • On the next transaction save/update, the ORM automatically writes it back encrypted with v2.
  4. Non-Blocking Background Re-Keying Worker:
    • An asynchronous background job (POST /api/v1/auth/rotate-keys/rekey-all) iterates through remaining enc:v1:... records in batches of 500 rows.
    • It re-encrypts rows from v1 to v2 without holding global table locks, allowing uninterrupted user usage.
    • Once all rows are at v2, historical key v1 is permanently purged.

3. Precision & Data Integrity Impact ​

Idempotency & Re-entrancy ​

  • All ciphertexts use standard format prefixing: enc:v1:<nonce_hex>:<tag_hex>:<ciphertext_hex>.
  • The TypeDecorator inspects the prefix on process_bind_param. If a value is already encrypted, it will not double-encrypt.
  • The Alembic backfill migration is fully idempotent: records containing enc:v1: are skipped during backfill.

Backward Compatibility ​

  • Existing API response schemas (Pydantic models) remain 100% unchanged. Pydantic receives decrypted plain strings from SQLAlchemy models.
  • Mobile and Web clients require zero protocol modifications.

4. Precision Review Checklist ​

  1. Is it Idempotent?
    • Yes. Ciphertext prefixing prevents re-encryption loops. Database backfill scripts can be re-run safely if interrupted.
  2. Is it Verifiable?
    • Yes. Automated test suite will assert that raw SQL execution (SELECT email, full_name, latitude, longitude FROM users;) returns enc:v1:... strings, while ORM queries return decrypted plaintext.
  3. Is it Scalable?
    • Yes. Because numeric amounts, dates, and category foreign keys remain unencrypted, PostgreSQL index scans and aggregations run at native C speeds ($<5\text{ ms}$). AES-256-GCM hardware acceleration (AES-NI) on modern CPUs encrypts/decrypts in nanoseconds.

5. Unresolved Questions & Decisions ​

  1. Blind Index Salt Rotation:
    • The BLIND_INDEX_SALT must be managed as an environment secret. If rotated, companion _bindex columns must be re-calculated via a maintenance migration script.
  2. Mobile Background Unseal Strategy:
    • Should the Android / iOS mobile app background sync silently ping /api/v1/mobile/sync on device boot to unseal the tenant after a server restart? (Recommended: Yes, via WorkManager).
