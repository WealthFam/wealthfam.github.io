Implementation Plan: 422 Error Log Hygiene & Core Security Hardening (Options B & D) ​

This plan details the implementation strategy for:

  1. Option B: 422 Validation Error Log Hygiene (Backend/app/main.py)
  2. Option D: Core Security — CORS Lockdown & Hardcoded Secret Cleanup (Backend, Parser, Admin-Backend, Infra)

1. Option B: 422 Validation Error Log Hygiene (Backend/app/main.py) ​

1.1 Problem & Threat Vector ​

In Backend/app/main.py (lines 158–165):

python
@application.exception_handler(RequestValidationError)
async def validation_exception_handler(request, exc):
    logger.error(f"422 Validation Error at {request.url.path}: {exc.errors()}")
    logger.error(f"Request body: {exc.body}")
    return JSONResponse(
        status_code=422,
        content={"detail": exc.errors(), "body": str(exc.body)},
    )
  • Log Leakage: Whenever any endpoint fails request validation (e.g. malformed type, missing field), exc.body is printed in plaintext to stdout and container log streams. When this occurs on /api/v1/auth/login, /api/v1/auth/register, or /api/v1/finance/statements/upload, plaintext user passwords, PINs, and access tokens are permanently leaked into server logs.
  • Response Echoing: The JSON response includes "body": str(exc.body), unnecessarily returning raw request bodies back to the client or potential attackers.

1.2 Proposed Changes ​

  • In Backend/app/main.py:
    • Sanitize validation logging: Log only the endpoint path and sanitized validation error fields (loc, msg, type), strictly excluding exc.body.
    • Sanitize HTTP 422 response payload: Return standard FastAPI error structure {"detail": exc.errors()} without echoing body.
python
@application.exception_handler(RequestValidationError)
async def validation_exception_handler(request: Request, exc: RequestValidationError):
    # Log sanitized error locations and messages without exposing sensitive body payloads
    sanitized_errors = [
        {"loc": err.get("loc"), "msg": err.get("msg"), "type": err.get("type")}
        for err in exc.errors()
    ]
    logger.warning(f"422 Validation Error at {request.url.path}: {sanitized_errors}")
    return JSONResponse(
        status_code=422,
        content={"detail": exc.errors()},
    )

2. Option D: Core Security — CORS Lockdown & Hardcoded Secret Cleanup ​

2.1 Problem & Threat Vector ​

A. CORS Wildcard with Credentials ​

  • Across Backend/app/main.py, Parser/main.py, and Admin-Backend/app/main.py:
    python
    if "*" in origins:
    cors_params["allow_origin_regex"] = ".*"
    Coupled with "allow_credentials": True, this effectively permits any web origin on the internet to execute credentialed, authenticated cross-origin XMLHttpRequests/fetch requests against WealthFam APIs, completely defeating same-origin protections.

B. Insecure Hardcoded Defaults & Fallbacks ​

  • Backend/app/core/config.py: SECRET_KEY: str = "CHANGE_THIS_TO_A_SECURE_SECRET_IN_PRODUCTION"
  • Parser/config.py: SECRET_KEY: str = "CHANGE_THIS_TO_A_SECURE_SECRET_IN_PRODUCTION"
  • Admin-Backend/app/core/config.py: ADMIN_SECRET_KEY: str = "WEALTHFAM_ENTERPRISE_ADMIN_SECRET_KEY_2026"SECRET_KEY: str = "CHANGE_THIS_TO_A_SECURE_SECRET_IN_PRODUCTION"
  • Infra/docker/docker-compose.yml & Infra/advanced-stack/docker-compose.yml: ADMIN_PASSWORD=${ADMIN_PASSWORD:-admin123}SECRET_KEY=${SECRET_KEY:-CHANGE_THIS_IN_PROD}ADMIN_SECRET_KEY=${ADMIN_SECRET_KEY:-CHANGE_ADMIN_SECRET_IN_PROD}
  • If environment variables are omitted or misconfigured in production deployments, services quietly start with predictable default secrets, allowing attackers to forge arbitrary JWT session tokens or admin privileges.

2.2 Proposed Changes ​

A. Environment Flag & Fail-Fast Validation (Backend, Parser, Admin-Backend) ​

Add ENVIRONMENT: str = "development" (accepts production, staging, development, test, local).

  1. Backend/app/core/config.py:

    • Add ENVIRONMENT: str = "development".
    • Add Pydantic @model_validator(mode="after") verifying that if ENVIRONMENT == "production":
      • SECRET_KEY is not the default "CHANGE_THIS_TO_A_SECURE_SECRET_IN_PRODUCTION" or "CHANGE_THIS_IN_PROD".
      • SECRET_KEY is at least 32 characters in length.
      • ALLOWED_ORIGINS is not * and does not contain *.
      • Throws ValueError immediately on startup if insecure.

  2. Parser/config.py:

    • Add ENVIRONMENT: str = "development".
    • Add validation: In production, enforce non-default, 32+ character SECRET_KEY and non-wildcard ALLOWED_ORIGINS.

  3. Admin-Backend/app/core/config.py:

    • Add ENVIRONMENT: str = "development".
    • Add validation: In production, enforce that neither SECRET_KEY nor ADMIN_SECRET_KEY matches known defaults ("WEALTHFAM_ENTERPRISE_ADMIN_SECRET_KEY_2026", "CHANGE_ADMIN_SECRET_IN_PROD").

B. CORS Lockdown (Backend/app/main.py, Parser/main.py, Admin-Backend/app/main.py) ​

  • If ENVIRONMENT == "production":
    • allow_origin_regex wildcard is strictly disabled.
    • Require explicit domain origins parsed from settings.ALLOWED_ORIGINS (e.g. https://app.wealthfam.com, https://admin.wealthfam.com).
    • If * is supplied with allow_credentials=True in production, raise a startup error.
  • If ENVIRONMENT in ("development", "test", "local"):
    • Default development origins to local Vite/Flutter ports: ["http://localhost:5173", "http://localhost:5174", "http://localhost:3000", "http://localhost:8080", "http://127.0.0.1:5173"].
    • Maintain developer convenience with warning logs if wildcard regex is used locally.

C. Clean Docker Compose Secret Fallbacks (Infra) ​

  • Infra/docker/docker-compose.yml:
    • Remove insecure fallback strings :-CHANGE_THIS_IN_PROD, :-CHANGE_ADMIN_SECRET_IN_PROD, and :-admin123.
    • Require ${SECRET_KEY:?Error: SECRET_KEY must be set in .env}, ${ADMIN_SECRET_KEY:?Error: ADMIN_SECRET_KEY must be set in .env}, and ${ADMIN_PASSWORD:?Error: ADMIN_PASSWORD must be set in .env}.
  • Infra/advanced-stack/docker-compose.yml:
    • Remove :-admin123 fallback, requiring explicit ${ADMIN_PASSWORD}.

3. Verification & Test Plan ​

  1. 422 Validation Error Test:
    • Send invalid payloads to /api/v1/auth/login containing sensitive fake passwords: {"email": "invalid_email", "password": "super_secret_password_123"}.
    • Verify response is HTTP 422 with {"detail": [...]} and does not contain "body".
    • Inspect captured log stream to verify "super_secret_password_123" is never logged.
  2. CORS Security Tests:
    • Test CORS preflight (OPTIONS request) with origin https://evil.com:
      • Under ENVIRONMENT=production: Access-Control-Allow-Origin: https://evil.com must not be returned.
      • Under ENVIRONMENT=production: Whitelisted origin (e.g. https://app.wealthfam.com) returns proper CORS headers.
  3. Fail-Fast Secret Validation Tests:
    • Instantiate config with ENVIRONMENT="production" and default SECRET_KEY -> verifies ValueError raised immediately.
    • Instantiate config with ENVIRONMENT="production" and ALLOWED_ORIGINS="*" -> verifies ValueError raised immediately.
    • Instantiate config with ENVIRONMENT="development" -> boots cleanly with local development defaults.
  4. Regression Test Suite:
    • Run pytest Test-Suite/modules/ingestion/
    • Run pytest Test-Suite/modules/vault/
    • Run npm --prefix Docs run docs:build
