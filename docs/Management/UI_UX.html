WealthFam WealthCore UI/UX Manifesto ​

Aether V4 — Sovereign Wealth Command Center ​

Document type: Canonical UI/UX design specification Product: WealthFam — Personal Finance and Wealth Management Design system: Aether V4 / WealthCore Application framework: Vue 3 Primary styling system: Tailwind CSS Global design foundation: CSS custom properties and design tokens Component architecture: Reusable Vue components with headless primitives where needed State management: Pinia Charts: Chart.js Icons: Lucide Vue Next Typography: Inter

Status: Design specification to be reviewed and established before application-wide UI rework.

1. Vision and Philosophy ​

Aether V4 defines WealthFam as a premium, compact, high-clarity personal finance application.

WealthFam should feel like a sophisticated wealth management workspace: precise, calm, information-dense and trustworthy.

The application must not resemble a generic Material Design dashboard, a default Vuetify application or an oversized collection of rounded analytics cards.

The design should communicate financial information efficiently, provide predictable interactions and make complex financial data easy to understand.

Core principles ​

  1. Clarity over decoration — every visual element must serve a purpose.
  2. Depth over shadow — hierarchy comes from tonal surfaces, subtle borders and selective translucency.
  3. State over static — every interactive component has deliberate loading, empty, error, success and disabled states.
  4. Consistency over creativity — shared components follow common visual and behavioural standards.
  5. Compactness over wasteful space — maximise useful information per screen without compromising readability.
  6. Financial accuracy over visual novelty — amounts, currencies, dates, ownership and performance must remain unambiguous.
  7. Performance over effects — visual effects must not compromise responsiveness.
  8. Reuse over duplication — common visual patterns must be implemented through reusable components and tokens.
  9. Preservation over unnecessary replacement — visual rework must not remove existing features or alter business logic.
  10. Consumer invisibility over exposed plumbing — a WealthFam end-user should never need to know what the parser is doing under the hood. Technical engineering tools, regex pattern managers, sandbox testers, and DuckDB request inspection logs must never be exposed in the consumer-facing app. All parser operations belong exclusively in a dedicated internal developer/admin portal. Ingestion in the consumer app must feel seamless, magical, and silent.

These principles govern all design decisions throughout the application.

2. Scope ​

This specification applies to the complete WealthFam application.

It covers all existing routes, pages, components, layouts, dialogs, drawers, forms, tables, charts, notifications and responsive states.

Relevant application areas include:

  • Application shell and navigation.
  • Dashboard and financial summaries.
  • Transactions and transaction details.
  • Accounts and account balances.
  • Assets, liabilities and net worth.
  • Budgets and spending analytics.
  • Investments and portfolio information, where implemented.
  • Family, household and sharing workflows, where implemented.
  • Authentication and onboarding.
  • Reports and exports.
  • Settings and configuration.
  • Forms, search, filters and date selectors.
  • Loading, empty, error, success and permission states.

The repository determines the actual scope. Do not invent new modules or remove existing functionality to fit this document.

This document establishes design standards, not permission to change business workflows.

3.2 Vuetify migration direction ​

Vuetify must not remain the long-term foundation of the WealthFam visual component system.

The objective is to replace the default Vuetify-driven interface with a deliberately designed component layer whose dimensions, spacing, typography, shapes and states are controlled by Aether V4.

This does not authorise an immediate, uncontrolled removal of Vuetify.

During the migration:

  • Existing routes and features must continue working.
  • Existing Vue components must be inventoried before replacement.
  • Pinia stores, API integrations and business logic should remain unchanged unless a separate requirement explicitly authorises changes.
  • Existing forms, validation, permissions and financial calculations must be preserved.
  • Legacy Vuetify components may remain temporarily while their replacements are implemented and verified.
  • New or redesigned components must follow the Aether component system rather than introduce new Vuetify dependencies.
  • Vuetify must be removed from dependencies only after all required usages, directives, plugins, styles and component dependencies have been migrated and verified.

Do not combine a complete UI redesign with unrelated application architecture changes.

3.3 Tailwind responsibilities ​

Tailwind is responsible for:

  • Layout and responsive grids.
  • Flexbox and grid positioning.
  • Spacing and sizing.
  • Responsive visibility and arrangement.
  • Typography utilities.
  • Border and surface utilities.
  • Interactive state utilities.
  • Consistent application of the design tokens.

Tailwind is not a substitute for a design system.

Repeated patterns must be expressed through reusable Vue components and shared tokens rather than copied collections of utility classes.

3.4 Component library policy ​

Use custom Vue components for the primary WealthFam visual language.

Use a headless component library when a complex interaction would otherwise require substantial accessibility and keyboard-interaction work.

Evaluate available Vue-compatible options, such as Reka UI or Headless UI, against the actual requirements before selecting one. Do not install multiple overlapping primitive libraries without a documented need.

Headless primitives must not dictate the visual identity. All visual styling remains governed by Aether tokens.

4. Aether V4 Colour System ​

Aether uses a restrained Indigo/Violet brand palette with neutral surfaces and explicit semantic colours.

The initial palette is the starting point for implementation and must be validated for contrast and semantic consistency.

4.1 Light-theme foundation ​

Define additional tokens for primary and muted text, borders, dividers, focus states, hover surfaces, selected states and informational messages.

4.2 Semantic financial colours ​

Financial meaning must not be inferred from colour alone.

  • Income, expenses and transfers must remain distinguishable.
  • Investment performance must be separated conceptually from cash flow.
  • Debt must not automatically be represented as a loss.
  • A large transaction is not inherently an alert.
  • Gains and losses must be interpreted in the correct account and reporting context.
  • Charts must remain understandable without colour perception.

Provide accessible labels, signs, icons or other cues where needed.

4.3 Dark theme ​

The token architecture must support a future or existing dark theme without rewriting individual components.

Dark mode must use deliberately designed background, surface, text, border and semantic roles. Do not simply invert the light palette.

If dark mode already exists, preserve its functionality and migrate it to the shared token system. Otherwise, establish the tokens so dark mode can be added consistently when required.

5. Global Design Token Architecture ​

Every shared visual decision must be controlled centrally.

5.1 Token categories ​

Colour tokens ​

  • Brand colours.
  • Neutral palette.
  • Backgrounds and surfaces.
  • Text and muted text.
  • Borders and dividers.
  • Semantic states.
  • Financial indicators.
  • Chart series.
  • Interactive states.
  • Theme-specific overrides.

Typography tokens ​

  • Font family.
  • Font sizes.
  • Font weights.
  • Line heights.
  • Letter spacing.
  • Financial number formatting conventions.

Spacing and sizing tokens ​

  • Spacing scale.
  • Page padding.
  • Section spacing.
  • Card padding.
  • Input and button heights.
  • Sidebar widths.
  • Icon sizes.
  • Content widths.
  • Breakpoints.

Shape tokens ​

  • Border radii.
  • Border widths.
  • Focus ring dimensions.
  • Surface outlines.

Elevation tokens ​

  • Shadow levels.
  • Glass effects.
  • Overlay emphasis.
  • Layering and stacking order.

Motion tokens ​

  • Transition durations.
  • Easing.
  • Hover transitions.
  • Loading animations.
  • Reduced-motion behaviour.

5.2 Global CSS structure ​

Adapt the following structure to the existing repository:

  • src/styles/tokens.css — foundational design tokens.
  • src/styles/themes.css — light and dark theme overrides.
  • src/styles/base.css — reset, typography, body defaults and focus behaviour.
  • src/styles/utilities.css — justified application-specific utilities.
  • src/styles/components.css — shared global component styles only when needed.

Component-specific styles may remain alongside Vue components where that improves encapsulation.

The above filenames are conventions, not a requirement to duplicate existing files that already fulfil these responsibilities.

5.3 Token rules ​

  • Raw colour codes must not be scattered throughout application components.
  • Repeated dimensions must use tokens or standard Tailwind utilities mapped to the design system.
  • Do not create separate, competing colour definitions in Tailwind configuration and global CSS.
  • Avoid arbitrary pixel values when a shared token or standard utility is suitable.
  • Avoid unnecessary inline styles.
  • Avoid widespread use of !important.
  • Do not duplicate Tailwind utilities with redundant CSS declarations.
  • Document justified exceptions.

CSS custom properties are the shared source of truth. Tailwind must reference these tokens.

6. Layout and Structural Hierarchy ​

6.1 Page container and width standards ​

The application enforces a single, canonical container governed by MainLayout.vue and .wf-page-container:

  • Single Source of Truth: MainLayout.vue provides <div class="wf-page-container py-4 sm:py-5"> around <slot />.
  • Canonical Maximum Width: 1600px (--wf-container-max-width: 1600px).
  • Canonical Horizontal Padding:
    • Desktop (≥1280px): px-8 (32px).
    • Tablet (≥768px): px-6 (24px).
    • Mobile: px-4 (16px).
  • Section Spacing: space-y-4 or space-y-5 (16–20px).

Critical Layout Rule & Anti-Pattern: ​

Views wrapped in MainLayout MUST NOT declare their own outer container with arbitrary max-widths (max-w-7xl, max-w-6xl, etc.) or duplicate padding (px-4 sm:px-6 py-6).

  • ❌ Forbidden Anti-Pattern:
    html
    <MainLayout>
  <div class="max-w-7xl mx-auto px-4 sm:px-6 py-6 space-y-6"> <!-- DO NOT DO: artificially narrows to 1280px and duplicates padding -->
  • ✅ Canonical Standard Pattern:
    html
    <template>
  <MainLayout>
    <div class="space-y-4"> <!-- or space-y-5 -->
      <!-- Header, KPIs, Toolbar, and Content -->
    </div>
  </MainLayout>
</template>

This guarantees consistent 1600px alignment and edge margins across Dashboard.vue, Transactions.vue, Accounts.vue, and all other views.

6.2 Page hierarchy ​

Use the following general hierarchy where appropriate:

  1. Breadcrumbs or contextual navigation.
  2. Page title and short description.
  3. Primary page actions.
  4. Search, filters and date controls.
  5. Main financial content.
  6. Secondary information and supporting actions.

Not every page needs every element. Preserve the information hierarchy appropriate to the actual workflow.

6.3 Compactness requirement ​

Every screen must be reviewed for wasted space.

Avoid:

  • Excessive vertical gaps.
  • Oversized headings.
  • Large empty cards.
  • Unnecessary card wrappers.
  • Repeated labels that add no information.
  • Excessive padding inside tables.
  • Redundant descriptions.
  • Large decorative illustrations in routine finance workflows.

Compactness must not result in unreadable text, inaccessible controls or ambiguous financial values.

7. Typography ​

Use Inter as the primary font, with sensible system fallbacks.

7.1 Type scale ​

Page title26–32px, weight 700–800

Use the lower end of the scale for dense workflows and the higher end only when hierarchy benefits from it.

Do not use extremely heavy text weights throughout the interface.

7.2 Financial number display ​

  • Prefer tabular numerals.
  • Right-align monetary values in tables and comparative lists.
  • Use consistent decimal precision within a given context.
  • Format currencies according to the account or report locale.
  • Support Indian currency presentation, such as ₹1,25,000, where appropriate.
  • Distinguish rounded summary figures from exact transaction values.
  • Never alter underlying financial values for presentation purposes.

Use a shared financial-value component when multiple screens need the same formatting, signs, currency and accessibility behaviour.

8.3 Control sizing ​

Use compact desktop controls by default.

Taller controls are appropriate where touch usability, accessibility or a specific interaction requires them. Do not make every input 56px tall or every button 48px tall.

9. Glassmorphism ​

Glassmorphism is an optional surface treatment within Aether, not the default component appearance.

9.1 Premium glass ​

The initial glass concept uses:

  • A translucent background.
  • Backdrop blur around 24px.
  • Moderate saturation enhancement.
  • A subtle one-pixel border.
  • Restrained shadow.
  • A deliberate corner radius.

All values must be controlled through tokens or shared component styles.

Use correct CSS colour-channel syntax when deriving translucent colours from theme variables. Do not assume a Vuetify variable or CSS custom property contains a directly usable complete colour.

9.2 Appropriate uses ​

Glass may be used for:

  • Floating navigation.
  • Contextual toolbars.
  • Selected dashboard emphasis panels.
  • Floating overlays.
  • Special contextual controls.

9.3 Restricted uses ​

Prefer opaque surfaces for:

  • Transaction tables.
  • Forms.
  • Dense reports.
  • Long text.
  • Data-heavy panels.
  • Content requiring consistent contrast.

9.4 Performance ​

  • Reduce or disable backdrop blur on mobile and constrained hardware.
  • Provide opaque fallbacks.
  • Avoid nested glass effects.
  • Avoid expensive animation of large translucent surfaces.
  • Maintain text contrast regardless of the underlying content.

10. Buttons and Actions ​

All buttons must use consistent dimensions, typography, state behaviour and icon rules.

10.1 Variants ​

  • Primary filled.
  • Secondary tonal.
  • Outlined.
  • Text.
  • Icon-only.

10.2 Icon policy ​

Use Lucide Vue Next consistently.

Use icons when they improve recognition, scanning or navigation. Do not require a prepend icon on every text button.

Actions such as Add, Edit, Delete, Search, Filter, Export and navigation commonly benefit from icons.

Save, Cancel, Apply and Confirm can remain text-only where the text is sufficiently clear.

Icon-only controls require:

  • Accessible names.
  • Tooltips where necessary.
  • Visible focus states.
  • Consistent hit areas.

10.3 States ​

Every button must have appropriate:

  • Default.
  • Hover.
  • Focus-visible.
  • Pressed.
  • Disabled.
  • Loading.

Avoid excessive glow, scaling and decorative animation.

Destructive actions must be recognisable and appropriately confirmed.

11. Forms and Inputs ​

Forms must be compact, predictable and accessible.

Standards ​

  • Consistent labels and field heights.
  • Consistent spacing between fields.
  • Clear required-field indicators.
  • Inline validation and error messages.
  • Predictable disabled and loading states.
  • Suitable numeric and currency handling.
  • Preservation of entered values where possible.
  • Prevention of duplicate submissions.
  • Accessible keyboard navigation.

Search inputs may use pill shapes where appropriate. Standard form inputs should use the shared input-radius token.

Do not independently style the same type of field across different pages.

12. Navigation ​

12.1 Sidebar ​

  • Expanded width: approximately 220–240px.
  • Collapsed rail: approximately 64–72px.
  • Consistent Lucide icons.
  • Clear active-route indication.
  • Tooltips for icon-only navigation.
  • Predictable grouping of related modules.
  • No unnecessary separators or nested navigation.

Preserve every existing route, permission and navigation capability.

12.2 Responsive rules ​

Initial layout rules:

  • Below 600px: mobile navigation and stacked content.
  • From 600px to below 1264px: collapsed rail or compact navigation where appropriate.
  • At 1264px and above: full desktop navigation where space permits.

Actual available space and content requirements must take precedence over blindly applying breakpoints.

12.3 Page navigation ​

  • Consistent page titles and primary actions.
  • Breadcrumbs for meaningful hierarchy.
  • Tabs for closely related views.
  • Predictable back navigation.
  • Preservation of relevant filters and page context.

13. Dashboard Design ​

The dashboard should provide a concise, high-density overview of the user's financial position as an executive command center.

Use the existing financial model and supported metrics.

Where implemented, prioritise:

  • Net worth and portfolio growth.
  • Real-time financial intelligence & anomaly detection.
  • Proportional health cockpit gauges.
  • Expense trajectory and daily burn rate dynamics.
  • Single continuous past-to-future cashflow timeline.
  • Credit wallet, statement balances, and liquidity headroom.
  • Assets, liabilities, and monthly cash flows.

13.1 Canonical Dashboard Patterns ​

  1. Financial Intelligence Horizontal Bar:
    • Single-line horizontal ticker displaying AI-driven budget alerts, liquidity suggestions, and caching status.
    • Prominent status indicators (Live vs Cached) and a dedicated instant refresh action.
  2. Proportional Cockpit Gauges (Wealth Compass):
    • 2x2 multi-ring vector cockpit instrument (Savings Rate, Portfolio XIRR, Credit Bureau Health, Budget Discipline).
    • Composite health score with color-coded status badges (Optimal, Moderate, Attention).
  3. Expense Trajectory & Cashflow Dynamics:
    • 8-column primary dynamics widget with 3 interactive view modes (6M Trajectory, Monthly Compare, MTD Pace).
    • 4 summary KPI badges (6-Mo Avg, Daily Burn Rate, Peak Month, Invest/Spend Ratio).
  4. Single Continuous Cashflow & Activity Timeline:
    • Chronological flow: Past Settled History (left) → Glowing Today Marker (center) → Upcoming Due Obligations (right).
    • Compact cards (185px–210px), auto-centering on Today (scrollToNow()), and category filter tabs.
  5. Credit Wallet & Liquidity Headroom Cockpit:
    • Bank-branded compact cards (215px–230px, e.g. HDFC, ICICI, Axis, SBI, Amex) with EMV chip & contactless glyphs.
    • Bureau 30% safe threshold meter, statement balance vs unbilled spend tracking, and toggleable Statement Matrix table view.
    • Header summary ribbon with matched h-8 controls (Limit, Due, Available, Manage ↗).

Rules ​

  • Avoid excessive empty or tall KPI cards.
  • Give key financial values clear hierarchy.
  • Keep supporting descriptions concise.
  • Use consistent date ranges and tabular numerals.
  • Make relevant summaries navigable to detail views.
  • Provide useful empty and loading states.
  • Keep the dashboard compact on standard laptop displays (max-w-[1600px]).

14. Transactions and Tables ​

Financial tables must prioritise scanning, comparison, and accuracy.

14.1 Canonical Ledger Patterns ​

  1. Integrated Compact Toolbar:
    • Single-row h-8 toolbar combining Search input, Account dropdown, Category dropdown, Time range select, Record counter, and Primary actions (Import CSV, + Add Transaction).
  2. Quick Category Filter Pills:
    • Horizontally scrollable 1-click filter pills with category icons/emojis + active filter tags with instant ✕ dismissal.
  3. Collapsible Forecast Drawer:
    • Spending velocity & 30-day forecast chart accessible via a toggle button, preserving the primary viewport fold for the transaction table by default.
  4. High-Density Table Rows:
    • Compact row height (py-2 px-3), category avatar pills with subtle color tints, clickable merchant deep-links (/merchants/...), inline detail tags (Account, #Ref, 🔄 Transfer, 🚫 Hidden, 🏦 EMI), right-aligned tabular amounts (+ / -), and row action shortcuts.
  5. Standardized Pagination:
    • Compact h-7 footer with page size selection (10, 25, 50, 100), record counters (Showing 1–25 of 142), and navigation controls.

Standards ​

  • Compact, readable rows.
  • Right-aligned monetary values with tabular numerals.
  • Consistent dates and currency formatting.
  • Clear sorting indicators on interactive columns.
  • Predictable filters and search with clear-all capabilities.
  • Accessible keyboard navigation.
  • Clear loading skeletons, empty states, and error alerts.
  • Subtle row hover and selection styling.

Avoid excessive cell padding, unnecessary badges, and decorative backgrounds on every row.

Preserve existing transaction editing, bulk actions, filtering, pagination, and other workflows.

15. Charts and Analytics ​

Chart.js remains the charting library.

Visual standards ​

  • Primary line thickness: approximately 3px.
  • Dashed comparison lines where useful.
  • Consistent semantic palette.
  • Restrained gridlines.
  • Clear axes, legends and tooltips.
  • Proper currency and date formatting.
  • Consistent period selectors.
  • Responsive chart dimensions.

Data integrity ​

  • Distinguish actuals from forecasts.
  • Distinguish cash flow from investment returns.
  • Make comparison periods explicit.
  • Do not hide meaningful negative values.
  • Do not communicate meaning through colour alone.
  • Ensure charts and adjacent summaries use consistent data and filters.

Avoid unnecessary chart recreation and repeated rendering.

16. Elevation ​

Aether uses three levels.

Base — Flat: Main canvas, tables and standard content.

Mid — Layered: Cards, contextual panels and selected glass surfaces.

High — Emphasis: Dialogs, overlays and rare high-priority states.

Prefer tonal separation and borders over heavy shadows.

Glow must remain exceptional. It must never substitute for meaningful hierarchy or accessible focus indicators.

17. Interaction and Application States ​

All interactive components must define their applicable states.

  • Default.
  • Hover.
  • Focus-visible.
  • Active.
  • Selected.
  • Disabled.
  • Loading.
  • Success.
  • Warning.
  • Error.
  • Empty.
  • Permission restricted.

Loading ​

Use skeleton loaders for substantial content regions where they improve perceived responsiveness.

Skeletons should resemble the expected final layout and minimise layout shifts.

Feedback ​

  • Use consistent success and error messages.
  • Explain recoverable errors clearly.
  • Preserve user input wherever possible.
  • Confirm destructive actions.
  • Avoid excessive notifications.

Motion ​

Use short, purposeful transitions.

Respect reduced-motion preferences and avoid animations that make financial values difficult to read.

18. Performance ​

  • Avoid unnecessary backdrop blur.
  • Debounce expensive searches where appropriate.
  • Avoid debouncing every interaction indiscriminately.
  • Avoid unnecessary reactive recomputation.
  • Lazy-load appropriate routes and heavy modules.
  • Prevent repeated Chart.js initialisation.
  • Use pagination or virtualisation for large datasets.
  • Avoid layout shifts during loading.
  • Keep icon and font loading efficient.

Measure performance before and after substantial changes. Do not claim improvements without evidence.

19. Responsive Behaviour ​

Mobile — below 600px ​

  • Stack content vertically.
  • Use approximately 16px page padding.
  • Minimise glass effects.
  • Keep monetary values readable.
  • Use mobile-friendly navigation.
  • Prevent horizontal overflow.
  • Make dialogs and forms fit the viewport.
  • Adapt wide tables without removing essential information.

Tablet — 600px to below 1264px ​

  • Collapse navigation when necessary.
  • Adapt grids to available width.
  • Reduce redundant spacing.
  • Maintain readable charts and tables.
  • Preserve usable control dimensions.

Desktop — 1264px and above ​

  • Use full navigation where appropriate.
  • Use available horizontal space efficiently.
  • Apply the 1600px content maximum where suitable.
  • Prefer compact financial summaries and aligned tables.
  • Avoid excessive whitespace on wide displays.

Validate layouts at representative viewport widths.

20. Accessibility ​

Accessibility is mandatory.

  • Target WCAG 2.2 AA where applicable.
  • Maintain sufficient contrast.
  • Provide visible keyboard focus.
  • Label icon-only controls.
  • Associate inputs with labels and validation messages.
  • Use semantic headings and tables.
  • Support keyboard navigation of menus and dialogs.
  • Avoid colour-only communication.
  • Respect reduced-motion preferences.
  • Maintain usability with zoomed text.
  • Verify touch and pointer interactions.

Compactness and decorative effects must never compromise accessibility.

21. Forbidden Patterns ​

Unless a documented exception is approved, prohibit:

  • Raw colour codes scattered throughout Vue components.
  • Duplicate token definitions.
  • Unnecessary inline styles.
  • Vuetify as the foundation for new Aether UI components.
  • Competing styling systems.
  • Excessive shadows, gradients, glow or blur.
  • Glass effects on every surface.
  • Oversized controls throughout dense workflows.
  • Mandatory icons on every text button.
  • Misaligned financial values.
  • Ambiguous currency displays.
  • Colour-only status indicators.
  • Unnecessary animation.
  • Arbitrary corner-radius values.
  • Duplicated shared components.
  • Uncontrolled CSS overrides.
  • Removal of existing functionality to simplify the design.

22. Quality Assurance and Design Validation ​

Before any application-wide UI rework, the design foundation must be reviewed and agreed upon.

The initial validation should include representative examples of:

  • A dashboard.
  • A dense financial table.
  • A form.
  • A dialog or drawer.
  • A chart.
  • A settings page.
  • A mobile layout.

These examples must demonstrate the intended typography, spacing, density, surface treatments, controls, states and responsive behaviour.

Once the foundation is validated, use the same system across all discovered routes.

Testing requirements ​

Use the existing test framework wherever possible.

Verify:

  • Token consistency.
  • Theme behaviour.
  • Shared component states.
  • Layout and radius consistency.
  • Responsive overflow.
  • Keyboard navigation.
  • Form validation.
  • Dialog and navigation behaviour.
  • Financial formatting.
  • Existing calculations and workflows.
  • Authentication and permissions.
  • Loading, empty and error states.

Where available, use visual regression tests or representative screenshot comparisons.

Distinguish pre-existing defects from newly introduced regressions.

23. Definition of Done ​

The Aether V4 design system is established when:

  1. The design tokens and global styling architecture are defined.
  2. Tailwind is configured to consume the central tokens.
  3. The reusable Vue component architecture is documented.
  4. The Vuetify migration strategy is clear and incremental.
  5. Representative screens demonstrate the intended compact visual language.
  6. Responsive behaviour and accessibility have been reviewed.
  7. Existing application behaviour is preserved.
  8. Testing requirements are documented.
  9. Migration progress and exceptions are traceable.
  10. The implementation can be expanded consistently across the entire application.

Do not claim complete migration while routes or legacy component dependencies remain unverified.

Final Philosophy ​

Clarity > Decoration

Depth > Shadow

State > Static

Consistency > Creativity

Compactness > Wasteful Space

Financial Accuracy > Visual Novelty

Performance > Unnecessary Effects

Aether V4 is the visual and behavioural contract for the entire WealthFam application. Every component, route and interaction must contribute to a consistent, compact and trustworthy financial experience.
